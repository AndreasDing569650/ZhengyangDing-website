Matching Parents and Children with SQL in Python

SQL Tutorial
Intergenerational income
Published

October 22, 2026

Introduction

How can we connect children to their biological parents in data that follow people over time? And once we make that connection, how similar are the incomes of parents and their children?

These questions matter because intergenerational income mobility tells us how strongly economic position is related across generations. To study it, we first need to know which parent records belong to which child. We then need income measures that represent more than a single unusual year.

This tutorial uses the Panel Study of Income Dynamics (PSID) and shows how to use SQL in Python with SQLite to build a parent-child match. After matching the two generations, I compare two ways to measure income: income in 2022 alone and average income across 2020 and 2022 (the 2021 survey reports family income for 2020, while the 2023 survey reports family income for 2022). I then use both measures to estimate intergenerational income elasticity (IGE).

The goal is to show how a few SQL operations can turn separate relationship and income files into a dataset that can answer an economic question.

Data and Matching Problem

The data come from the Panel Study of Income Dynamics (PSID). This project uses individual and family information for 2020 and 2022, along with a parent-identification file that records biological parent-child relationships.

The cleaned longitudinal file is organized by person and year. Its main variables are:

  • person_id: a permanent identifier for an individual across survey years
  • family_id: the family unit the individual belongs to in a particular year
  • family_income: total income of that individual’s family unit
  • year: survey year
  • age: the individual’s age in that year

It is important to distinguish person_id from family_id. A person keeps the same permanent person_id over time, but their family_id can change if their family living arrangement changes.

The permanent person identifier is built from the PSID’s 1968 family interview number (ER30001) and person number (ER30002). The parent-identification file uses the same two-part structure for each relationship:

Person Identifier components
Child PID2 and PID3
Biological mother PID4 and PID5
Biological father PID23 and PID24

Combining each pair into the same format—for example, 4_3—allows the child and parent identifiers to be matched to person_id in the longitudinal file. For an individual record, the same rule is applied to ER30001 and ER30002; for a parent-identification record, it is applied to the relevant PID pair.

The analysis creates two income measures. The first uses family income in 2022. The second averages family income in 2020 and 2022. For the final sample, the child’s age and the average age of the matched parent observations must both be between 25 and 64 in 2022. Parent observations are included only when the parent and child belong to different family units in the relevant year.

Loading the Data into SQLite

After the raw files have been cleaned, the two datasets are loaded into an SQLite database. The individual-level data are stored in an individual table. The parent-identification data are stored in a separate parent_identification table.

The cleaned individual_long.csv file already contains person_id, constructed from ER30001 and ER30002. The parent-identification file contains the original PID components, so I convert those components into the same ID format before loading the table.

import pandas as pd
import numpy as np
import sqlite3
import statsmodels.api as sm
from pathlib import Path

project_root = Path(r"ENTER YOUR PROJECT PATH")
cleaned_dir = project_root / "data" / "cleaned_data"

individual_data = pd.read_csv(
    cleaned_dir / "individual_long.csv"
)

parent_identification = pd.read_csv(
    cleaned_dir / "parent_identification.csv"
)

def make_person_id(family_id, person_number):
    if pd.isna(family_id) or pd.isna(person_number):
        return None

    family_id = int(family_id)
    person_number = int(person_number)

    if family_id <= 0 or person_number <= 0:
        return None

    return f"{family_id}_{person_number}"

# During individual-data cleaning, this same function is applied to:
# individual_data["person_id"] = individual_data.apply(
#     lambda row: make_person_id(row["ER30001"], row["ER30002"]),
#     axis=1
# )

parent_identification["child_id"] = parent_identification.apply(
    lambda row: make_person_id(row["PID2"], row["PID3"]),
    axis=1
)

parent_identification["mother_id"] = parent_identification.apply(
    lambda row: make_person_id(row["PID4"], row["PID5"]),
    axis=1
)

parent_identification["father_id"] = parent_identification.apply(
    lambda row: make_person_id(row["PID23"], row["PID24"]),
    axis=1
)

conn = sqlite3.connect(
    cleaned_dir / "psid_matching.db"
)

individual_data[
    ["person_id", "family_id", "family_income", "year", "age"]
].to_sql(
    "individual",
    conn,
    if_exists="replace",
    index=False
)

parent_identification[
    ["child_id", "mother_id", "father_id"]
].to_sql(
    "parent_identification",
    conn,
    if_exists="replace",
    index=False
)

The two tables have different jobs. The parent_identification table tells us who is related to whom. The individual table tells us each person’s family income, family membership, and age in each survey year.

Indexes are created on the identifiers used in the SQL joins. They help SQLite find matching records more efficiently.

cursor = conn.cursor()

cursor.execute("""
CREATE INDEX IF NOT EXISTS idx_individual_person_year
ON individual(person_id, year)
""")

cursor.execute("""
CREATE INDEX IF NOT EXISTS idx_parent_child
ON parent_identification(child_id)
""")

conn.commit()

Constructing the Parent-Child Relationship

The parent-identification file stores the biological mother and father in separate columns. I turn these two relationships into one bridge table called parent_child. This makes the next step easier because each row represents one child-parent link.

cursor.execute("DROP TABLE IF EXISTS parent_child")

cursor.execute("""
CREATE TABLE parent_child AS

SELECT
    child_id,
    mother_id AS parent_id,
    'mother' AS parent_type
FROM parent_identification
WHERE mother_id IS NOT NULL

UNION ALL

SELECT
    child_id,
    father_id AS parent_id,
    'father' AS parent_type
FROM parent_identification
WHERE father_id IS NOT NULL
""")

conn.commit()

UNION ALL stacks the mother records and father records. A child with both biological parents identified therefore appears twice: once for the mother and once for the father.

The bridge table tells us who is connected to whom. The individual table tells us what each person’s income, family membership, and age were in a given year. The SQL joins connect these two pieces of information.

A quick guide to the SQL operations

  • SELECT chooses which columns or calculated values should appear in the query result. Here, it selects the child ID, parent income, child income, and age.
  • JOIN connects records from different tables. I join the bridge table to individual to retrieve the parent’s and child’s observations.
  • GROUP BY puts rows with the same child ID into a group, so the query can produce one matched record for each child.
  • Aggregation, such as AVG(), calculates a summary for each group. Here, it averages the family income of the qualifying parent observations.

These operations work together: JOIN finds the relevant records, GROUP BY organizes them by child, and AVG() summarizes the parent observations.

Matching Parents and Children in 2022

I start with the single-year measure and use observations from 2022.

The query joins the parent_child bridge table to the individual table twice. The first join retrieves the parent’s 2022 record. The second retrieves the child’s 2022 record.

single_year_query = """
SELECT
    pc.child_id,

    AVG(parent.family_income)
        AS parent_income_2022,

    child.family_income
        AS child_income_2022,

    child.age
        AS child_age_2022,

    AVG(parent.age)
        AS parent_age_2022

FROM parent_child AS pc

JOIN individual AS parent
    ON pc.parent_id = parent.person_id
    AND parent.year = 2022

JOIN individual AS child
    ON pc.child_id = child.person_id
    AND child.year = 2022

WHERE parent.family_id != child.family_id

GROUP BY
    pc.child_id,
    child.family_income,
    child.age
"""

single_year = pd.read_sql_query(
    single_year_query,
    conn
)

The SELECT statement lists the information I want in the result. The two JOIN operations attach the parent’s and child’s 2022 records to the same child ID. The condition

WHERE parent.family_id != child.family_id

keeps parent observations only when the parent and child belong to different family units in 2022.

The query then uses GROUP BY to organize the qualifying parent observations by child. AVG(parent.family_income) calculates the average family income across the matched biological-parent observations that meet the family-separation condition. If both parent observations qualify, their family incomes are averaged; if only one qualifies, that observation supplies the parent-income measure. This is an average of family-unit income, not the sum of the parents’ personal earnings.

The child’s income is the family income of the family unit the child belongs to in 2022. The query also calculates the average age of the qualifying parent observations. These variables are returned as parent_income_2022, child_income_2022, child_age_2022, and parent_age_2022.

Constructing the 2020–2022 Income Measure

The second measure uses both 2020 and 2022. Instead of relying on income from one survey year, I first retrieve the income observations for each generation in both years.

multi_year_query = """
SELECT
    pc.child_id,

    AVG(parent_2020.family_income)
        AS parent_income_2020,

    AVG(parent_2022.family_income)
        AS parent_income_2022,

    child_2020.family_income
        AS child_income_2020,

    child_2022.family_income
        AS child_income_2022,

    child_2022.age
        AS child_age_2022,

    AVG(parent_2022.age)
        AS parent_age_2022

FROM parent_child AS pc

JOIN individual AS parent_2020
    ON pc.parent_id = parent_2020.person_id
    AND parent_2020.year = 2020

JOIN individual AS parent_2022
    ON pc.parent_id = parent_2022.person_id
    AND parent_2022.year = 2022

JOIN individual AS child_2020
    ON pc.child_id = child_2020.person_id
    AND child_2020.year = 2020

JOIN individual AS child_2022
    ON pc.child_id = child_2022.person_id
    AND child_2022.year = 2022

WHERE
    parent_2020.family_id != child_2020.family_id
    AND parent_2022.family_id != child_2022.family_id

GROUP BY
    pc.child_id,
    child_2020.family_income,
    child_2022.family_income,
    child_2022.age
"""

multi_year = pd.read_sql_query(
    multi_year_query,
    conn
)

This query uses four joins because it needs a record for the parent and the child in each of the two years. Since these are inner joins, a matched child-parent relationship must have observations in both 2020 and 2022.

The WHERE conditions apply the family-separation rule in each year. The parent observations used in the calculation must belong to a different family from the child in both 2020 and 2022.

The query returns parent and child income separately for each year. Python then calculates the simple two-year average:

multi_year["parent_income_avg"] = (
    multi_year["parent_income_2020"]
    + multi_year["parent_income_2022"]
) / 2

multi_year["child_income_avg"] = (
    multi_year["child_income_2020"]
    + multi_year["child_income_2022"]
) / 2

Finally, I merge the single-year and multi-year results using child_id:

matched_data = single_year.merge(
    multi_year,
    on="child_id",
    how="inner"
)

The inner merge keeps children who have both measures. This gives us a common starting sample for comparing the 2022 income measure with the 2020–2022 average.

Applying the Sample Restrictions

Before running the regressions, I keep observations with positive income. This is necessary because the models use the natural logarithm of income, which is not defined for zero or negative values.

matched_data = matched_data[
    (matched_data["parent_income_2022"] > 0) &
    (matched_data["child_income_2022"] > 0) &
    (matched_data["parent_income_avg"] > 0) &
    (matched_data["child_income_avg"] > 0)
].copy()

I then apply the working-age restriction using 2022 age:

matched_data = matched_data[
    matched_data["child_age_2022"].between(25, 64) &
    matched_data["parent_age_2022"].between(25, 64)
].copy()

Here, child_age_2022 is the child’s age, while parent_age_2022 is the average age of the qualifying parent observations. Both measures must fall between 25 and 64.

One important step is to build both regression samples from this same filtered matched dataset. This keeps the single-year and multi-year estimates comparable.

single_year = matched_data[
    [
        "child_id",
        "parent_income_2022",
        "child_income_2022"
    ]
].copy()

multi_year = matched_data[
    [
        "child_id",
        "parent_income_avg",
        "child_income_avg"
    ]
].copy()

Estimating Intergenerational Income Elasticity

Now that the parent-child match and income measures are ready, I estimate how strongly parents’ income is associated with their children’s income.

I use a log-log regression:

\[ \log(Y_i^{child}) = \alpha + \beta\log(Y_i^{parent}) + \varepsilon_i. \]

The coefficient () is the intergenerational income elasticity (IGE). For example, an IGE of 0.25 means that a 1% difference in parental income is associated with about a 0.25% difference in child income, on average.

For the 2022 single-year measure, I take the natural log of parent and child income and estimate the model using OLS:

single_year["log_parent_income"] = np.log(
    single_year["parent_income_2022"]
)

single_year["log_child_income"] = np.log(
    single_year["child_income_2022"]
)

X_single = sm.add_constant(
    single_year["log_parent_income"]
)

model_single = sm.OLS(
    single_year["log_child_income"],
    X_single
).fit()

I repeat the same steps using the 2020–2022 average:

multi_year["log_parent_income"] = np.log(
    multi_year["parent_income_avg"]
)

multi_year["log_child_income"] = np.log(
    multi_year["child_income_avg"]
)

X_multi = sm.add_constant(
    multi_year["log_parent_income"]
)

model_multi = sm.OLS(
    multi_year["log_child_income"],
    X_multi
).fit()

For each model, I record the IGE estimate, standard error, p-value, number of observations, and R-squared. The two models use the same filtered matched sample, so the comparison focuses on the income measure rather than a change in the sample.

Results

The two models produce the following estimates:

Income measure Observations IGE Standard Error R-squared
2022 single-year income 1,635 0.245 0.023 0.065
2020–2022 average income 1,635 0.280 0.022 0.092

With 2022 income alone, the estimated IGE is 0.245. This means that a 1% difference in parental family income is associated with about a 0.245% difference in child family income.

When income is averaged across 2020 and 2022, the estimated IGE rises to 0.280. In this specification, a 1% difference in parental family income is associated with about a 0.280% difference in child family income.

The R-squared also rises from 0.065 to 0.092. In this sample, the model using the two-year average accounts for more of the variation in child income. Overall, the estimates show that the measured intergenerational relationship depends partly on how income is measured.

Life-Cycle Bias

Income changes over a person’s working life. Someone who is just starting a career may earn much less than they will later on. Someone further along in their career may be closer to their peak earnings. A single year’s income can therefore reflect when we observe a person, not just their longer-run economic position.

This creates a problem for intergenerational income estimates. If we measure parents’ and children’s income at only one point in time, the estimate may be influenced by the life-cycle stages they happen to be in. A one-year snapshot can make long-run income differences look larger or smaller than they really are.

Averaging income across years can help. It reduces the influence of an unusual year and makes the measure less dependent on one particular observation. In this project, the two-year average gives an IGE of 0.280, compared with 0.245 using 2022 income alone. The higher estimate is consistent with the idea that a single-year measure may understate the persistence of income across generations in this sample.

This comparison illustrates why life-cycle timing and short-term income variation matter when measuring IGE. It does not show that averaging two years removes every source of life-cycle bias, but it does show that the estimated relationship changes when we use a measure that is less dependent on a single year’s income.

Takeaways

This project shows how SQL in Python can turn separate PSID relationship and income files into a matched parent-child dataset.

The process is straightforward:

  1. Create a permanent person_id so the same individual can be followed across survey years.
  2. Use the parent-identification file to build a bridge table linking each child to their biological mother and father.
  3. Use SQL SELECT and JOIN to retrieve the parent and child records.
  4. Use GROUP BY and AVG() to summarize the qualifying parent observations and construct the parental income measure.
  5. Compare IGE estimates using 2022 income alone and the average of 2020 and 2022 income.

The main takeaway is that the way we measure income matters. In this sample, the IGE is higher when income is averaged across two years rather than measured in 2022 alone. A multi-year average can give a more stable picture of long-run economic status because it relies less on one year’s income. SQL makes the matching process organized and transparent, while the final regression connects the matched data to the economic question.
